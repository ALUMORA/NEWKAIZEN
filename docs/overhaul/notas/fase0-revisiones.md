## Defectos

- The visual gate is too loose to catch real content regressions, and this is demonstrated, not just the theoretical tall-page case the stream disclosed. With /rf removed from the HAR, the Sharpe desktop screen changes a lot: the sidebar shows 'Sin conexión' with a red dot instead of 'Backend OK', and the rate reads '8.60% (ref. fija, sin backend)' instead of '9.16% (ago 2026)'. That is 9,311 differing pixels (0.72%) against the 25,920 pixels that maxDiffPixelRatio 0.02 allows on a 1440x900 page. expect(page).toHaveScreenshot passed, and only the console and network guards failed the test. Any regression that doesn't trip a guard, such as a wrong number or a changed label, will pass the baseline. Fix in playwright.config.js:107 or per call in e2e/baseline.spec.js:53: use a small absolute maxDiffPixels (for example 50) with the default threshold.
- The new .github/workflows/check.yml will be red on the first push or PR to main, analizavende or alumora. `ruff check .` reports 104 errors in backend.py (confirmed locally with ruff 0.16.8). The stream disclosed this, but the workflow ships a failing job. Before merge, either R0's pyproject.toml ruff config has to land first, or the ruff step has to be scoped or made non-blocking.
- The claim that runs are pixel-identical with zero tolerance is not reproducible. My zero-tolerance run (maxDiffPixels 0, threshold 0) failed legacy-portfolio mobile on 1 pixel at (5,820): G channel 38 vs 37, under the fixed bottom nav. It is harmless at 2%, but the stream's suggestion to tighten to zero tolerance would flake. Tighten with maxDiffPixels and keep the default threshold of 0.2.
- The baseline covers data-driven content on only 2 of 8 tabs. The recorder never presses run buttons, so Analytics vs SPY, Sharpe Optimizer, Análisis and FIBRA Screener are captured in their empty 'press to run' state (I viewed these four). ML Screener and Fórmula Mágica are probably the same, judging by size (about 50-85 KB PNGs at viewport height), but I did not view them. No backtest, optimizer, screener or analysis output from the legacy app is in the baseline. This is by design, but next streams should not treat those tabs as covered.
- Minor: `npm run e2e` runs `vite build --mode e2e` into the same dist/ that `npm run build` uses. After an e2e run, dist/ holds the e2e build pointed at VITE_API_URL=http://api.test, and a later `npm run bundle` or a manual deploy from dist/ would use it. Suggested fix: build:e2e with --outDir dist-e2e, and have the preview server use it.
- Minor, the open issue about .env.e2e is inaccurate. .env.e2e is tracked (git ls-files lists it, and git check-ignore exits 1), so later edits are not ignored by the `.env.*` rule. Adding `!.env.e2e` only helps if the file is ever removed and re-added.
- Minor: in e2e/baseline.spec.js:53-54, guards.assertClean() runs after toHaveScreenshot. If the screenshot fails, the guard's more precise cause (an aborted request, a console.error) is never reported. Separately, full-page captures draw the fixed sidebar and bottom nav only over the first viewport, so content under the mobile bottom nav at about y 790-844 is hidden in every mobile snapshot.

## Defectos

- The volatile-field masking hides deterministic data, so real regressions pass the goldens. find_volatile_paths in tests/replay/golden.py auto-masks 'news[*].time' in 8 goldens (7 get_news plus get_market_news) and 'asOf' in get_rf. Under replay both values come from recorded data and are fully deterministic: time is parsed from the provider's pubDate, and asOf is the FRED observation date. They do not depend on the clock. Checked: with every news time set to 0, multiplied by 1000 (ms instead of s) or set to None, compare() returns []. When backend.py's pubDate parse was mutated to 0, all 7 per-ticker get_news goldens still passed. With get_rf asOf changed to '1999-01-01', all 124 tests still passed. An S1 port that breaks timestamp parsing or the rate date would pass parity. Fix: since the clock is frozen, drop the name-based auto-volatility for these goldens and set volatile_paths to [].
- compare() does not enforce the documented volatile contract. The handoff says a volatile field 'must still exist with the same JSON type', but the volatile branch skips the type check whenever either side is None (`and None not in (a, e)` in tests/replay/golden.py compare). A field that becomes null therefore passes silently.
- live_match is weaker than the summary implies. In scripts/record_fixtures.py the 'live' result comes from record mode, where the backend already calls the ReplayTicker/FastInfoProxy stand-ins and every value is materialized through the same store encode/decode. live_match=true proves record-to-replay serialization fidelity. It does not prove the proxies behave like an unpatched yfinance backend: a proxy AttributeError swallowed by the backend's `except Exception` would show up the same on both sides. Also, --goldens-only copies live_match over from the old golden. I spot-checked the attributes the backend uses (info, fast_info.* including getattr(fast_info,'name'), history, statements, news, insider_transactions, institutional_holders) and they match the yfinance 1.7 surface, so no actual mismatch was found.
- Coverage gap: the RSS fallback path in backend.py (_rss_news, and get_market_news when yfinance returns fewer than 5 items) has no fixture and no golden. yfinance news was enough on 2026-09-22, so zero RSS keys were recorded (the only HTTP hosts are cboe, sec x2, fred and stooq). The summary lists RSS among the covered _session consumers. The patch would intercept those calls, but that parsing logic is not characterized, so B2's kaizen_api/providers/rss.py has no legacy parity baseline.
